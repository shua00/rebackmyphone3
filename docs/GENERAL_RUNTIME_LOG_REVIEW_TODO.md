# 非 P2P 运行日志分析与后续 TODO

> 分析依据：用户提供的两份 Android 运行日志，设备包括 ZTE A2023BH（Android 11/API 30）和 Redmi Note 8（Android 15/API 35），日志时间覆盖 2026-11-26 至 2026-11-28。日志对应旧构建 `20261126-0419-V2520`，不能直接推断当前分支 head 仍存在相同问题。

## 优先级较高

- [ ] **日志隐私脱敏**：默认禁止将短信正文写入普通运行日志；短信号码脱敏；精确经纬度、设备标识、Wi-Fi SSID 等敏感字段按最小必要原则记录。日志导出提供脱敏副本，避免改变原始本地日志；明确保留期限和清理策略。旧日志中可见短信正文及发送号码，属于已有证据支持的隐私风险。
- [ ] **定位新鲜度与上报成功状态分离**：区分网络上报成功与定位采集成功；每个定位值携带采集时间、来源、精度和 freshness 状态；陈旧坐标必须明确标记，不能让上层把 HTTP/服务器接收成功误认为实时定位成功。
- [ ] **陈旧定位使用策略**：核查主动刷新超时、旧值回退、定位 provider 降级与静止/运动状态调度。旧日志中 Redmi 曾在定位刷新持续超时的情况下，继续使用约 6 小时以上的旧坐标并显示上报成功。保留旧值可以，但必须显式携带年龄并由上层决定是否可用于轨迹、告警和状态判断。

## 后续可靠性改进

- [ ] **长时间离线的上报队列策略**：核查队列容量、过期、优先级、静止状态合并和恢复补发互斥。旧日志显示离线队列增长到约 24 条，之后有恢复补发和清理记录；基础机制有效，但需要明确最大容量及长期离线策略。
- [ ] **定位与上报离线降频**：网络长期不可用时避免无收益的高频主动定位刷新和重复上报唤醒；结合网络状态、运动状态、电量和定位新鲜度做有界退避。
- [ ] **服务生命周期诊断**：对 SERVICE_CREATE、TASK_REMOVED、JobScheduler、Alarm、无障碍唤醒和系统重启增加统一 session/serviceInstance 关联，记录可确认的启动来源、回调注册/注销结果和资源清理结果。旧日志存在多次服务重建/任务移除，但没有足够崩溃堆栈，不能据此认定发生崩溃。
- [ ] **网络监听异常分类**：将主动关闭 Socket 后的 EBADF 与非预期接收异常区分记录；关联 network generation、关闭原因、重新绑定结果。旧日志中多数 EBADF 紧随主动关闭和成功重绑定，暂不应一概当作故障。
- [ ] **Wi-Fi 扫描降级可观测性**：保留 startScan 失败时的缓存降级，补充失败原因/系统限制分类和缓存年龄；不因诊断而增加默认扫描频率或后台探测。

## 当前日志证据与判断边界

- 内存记录约 4–21 MB、存储可用空间约 65 GB，未见资源耗尽证据。
- 电池白名单多次显示开启；仅凭现有日志不能判断设备级后台策略完全正常。
- Wi-Fi `startScan=false` 有缓存降级记录，当前不构成必须立即重构的证据。
- Redmi 曾长时间离线，离线队列后来有补发清理迹象；需要后续验证队列上限和恢复时并发行为。
- ZTE/Redmi 服务多次重新创建，但缺少足够的进程死亡原因和 crash stack；先补诊断，不先假定崩溃根因。

## 实施约束

- 本文任务与 LAN P2P 数据面隔离，不应为处理这些 TODO 改动 P2P 协议、Listener、ACK 或文件传输路径。
- 先对照实施时的当前代码确认问题是否仍存在；旧日志结论不自动等于当前代码缺陷。
- 修改应保持简单网络快路径，不增加无关周期扫描、探测、线程、Socket 或网络流量。
- 涉及隐私字段时默认最小化采集；诊断开关不能成为默认采集敏感正文的理由。
